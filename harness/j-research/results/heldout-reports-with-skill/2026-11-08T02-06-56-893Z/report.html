I'd build a small Django app backed by PostgreSQL and run it with Docker Compose on your server. It's a few days to two weeks of work for one developer. Use Django's built-in local accounts instead of SSO.

## Why Django

- **Logins, permissions and an admin screen come built in.** With eight users, you can manage accounts, fix data and view the audit log in the admin without building any of those screens.
- **Forms, CSRF protection, migrations and CSV export are standard library or framework features.** You won't need a separate frontend framework. Server-rendered pages, plus htmx if you want something a bit nicer, are enough.
- **It's widely used and boring.** Whoever maintains it in three years will understand it.

If your team already knows Rails or Laravel, use that instead. Any of the three works. Pick the one someone on your team already knows.

## Data model (four tables)

| Table | Key fields |
|---|---|
| `User` | Django's built-in user model, plus a role or "can approve" flag |
| `PurchaseRequest` | requester, vendor, description, amount, currency, attachment (quote or invoice), status: `draft → pending_1 → pending_2 → approved → exported → paid`, or `rejected` / `cancelled` |
| `Approval` | request, step (1 or 2), approver, decision, comment, timestamp, **amount at the time of the decision** |
| `AuditEvent` | request, actor, action, before/after JSON, timestamp, IP. Rows are only ever added, never changed |

## Rules to enforce on the server

1. **Requesters can't approve their own requests**, and the two approvers must be different people.
2. **Approvals happen in strict order.** Step 2 can only act once step 1 has approved. A rejection at either step ends the request.
3. **Editing a request after submission clears all its approvals**, so the amount someone approved is the amount that gets paid. Storing the amount with each approval lets you prove this later.
4. **Every status change and the audit entry for it are saved together, or not at all**, so you can't end up with one and not the other. Put all status changes in one service function instead of spreading them across views, and lock the request row while it's being updated so two people clicking at once can't both act on it.
5. **Make the audit log hard to tamper with.** The app's database user should only be allowed to add rows to the audit table, never edit or delete them. This is a single `GRANT` statement and is worth doing.

## CSV export

- Export only **approved and not yet exported** requests. Each export creates a numbered batch and marks its requests `exported`, so nothing gets paid twice. After paying, someone marks the batch `paid`.
- Include: request ID, vendor, amount, currency, both approvers' names with dates, and the batch ID.
- **Neutralise spreadsheet formulas.** If a field starts with `=`, `+`, `-` or `@`, prefix it with `'`. Otherwise a vendor name could run as a formula when the file is opened in Excel.
- Let people re-download past batches so the finance team can reconcile against them.

## Deployment

- **Docker Compose** with three containers: the app (Gunicorn), Postgres, and **Caddy** for HTTPS (automatic certificates, or your internal CA if the server isn't public). Keep it on the internal network or VPN if you can.
- **Backups:** a nightly `pg_dump` plus the attachments folder, copied off the server. **Test a restore once.** This matters more than anything else on this list.
- **Email notifications** through your existing SMTP server, e.g. "you have a request to approve" and "your request was rejected". This is optional but makes the app much more useful.
- **Security basics:** strong passwords, Django's login rate limiting (or `django-axes`), and two-factor login via `django-otp` if the app is reachable from outside your network.

## Decide before building

1. **How are the two approvers chosen?** Options are a fixed pair for everyone, a pair per requester or department, or picked from a list when the request is submitted. A fixed rule plus a backup when someone is on leave is usually simplest.
2. **Do approvals depend on the amount?** For example, under a set limit only one approval is needed. Agree on this now even if the answer is "no".
3. **Is there a single currency**, and which fields does your bank's manual payment process actually need in the CSV?

## Simpler alternative

If you'd rather not maintain code, a self-hosted no-code tool like Budibase or NocoDB can do forms and approvals. But enforcing strict ordering, blocking self-approval and keeping a tamper-resistant audit trail tends to be awkward in those tools. For a process that controls payments, I'd still build the small Django app.

## Stack

- **Django**: comes with authentication, password reset, permissions and an admin screen for managing users. You don't need a separate frontend framework. Server-rendered templates, plus a little htmx if you want it, are enough.
- **PostgreSQL**: SQLite would handle the load, but Postgres makes the audit table easier to protect (see below) and backups are routine.
- **Docker Compose** with three containers: app, db and Caddy. Caddy handles HTTPS automatically, or with an internal certificate if the server isn't reachable from the internet.
- **SMTP** (optional): "you have a request to approve" emails, sent through your existing mail server.

## Data model

```
User                (Django built-in; add role flags: requester / approver / finance)
PurchaseRequest     id, requester, supplier, description, amount (Decimal), currency,
                    cost_code, attachment(s), status, created_at
ApprovalStep        request, order (1 or 2), approver, decision (pending/approved/rejected),
                    comment, decided_at
AuditEvent          request, actor, action, before (JSON), after (JSON), timestamp, ip
ExportBatch         id, created_by, created_at, file_hash, requests[]
```

**Status flow:** `draft → submitted → approved_1 → approved → exported → paid`, and a request can move to `rejected` from any approval step. Put every transition in one service function that checks the transition is allowed and writes the `AuditEvent` in the same database transaction. Views should never change `status` directly.

## Rules to enforce in code

1. **Order is enforced.** Approver 2 can't act until approver 1 has approved. Approver 2 should see the request but have no approve button until then.
2. **Separation of duties.** The requester can't approve their own request, and the two approvers must be different people. Check this on the server, not only in the UI.
3. **Edits after submission reset approvals.** If a request is changed after submission, it goes back to draft and existing approvals are cleared. Otherwise someone could change the amount after approval.
4. **Who approves.** With eight people, the simplest approach is a small configuration table. For example: approver 1 is the requester's manager, approver 2 is a named finance person. A threshold rule like "over £X needs the director" is easy to add later.

## Audit trail

- Make `AuditEvent` append-only. Revoke `UPDATE` and `DELETE` on that table for the app's database role. Then even a bug or a curious admin working through the app can't rewrite history.
- Log the actor, the timestamp, the action, and the before and after values for every change. That covers creating, editing, submitting, approving, rejecting, exporting and marking as paid.
- If you want tamper evidence, store a hash of the previous event with each new event. It's cheap to add, but optional at your size.
- Show the audit trail as a timeline on each request page, so people actually use it.

## CSV export

- Finance clicks "Export approved". This creates an `ExportBatch` containing every request that is `approved` and not yet exported, moves those requests to `exported`, and downloads the file. Because of the batch record, nothing gets paid twice or missed.
- Store the file's hash with the batch so you can later prove what was exported.
- After paying manually, finance marks the whole batch, or individual requests, as `paid`.
- **Escape formula injection.** Prefix any cell that starts with `=`, `+`, `-` or `@` with a `'`. Otherwise a supplier name could run as a formula when the file opens in Excel.
- Write amounts as plain decimals with a separate currency column. Never store money as a float.

## Operations

- **Backups:** a nightly `pg_dump` plus the uploaded attachments, copied off the server. Test a restore once.
- **Security:** sign-in is username and password. Add Django's TOTP two-factor login (`django-otp`) at least for approvers and finance, since they control money.
- **Deployment:** `git pull && docker compose up -d --build` is enough at this size.

One developer who knows Django should need about **1–2 weeks** to reach a usable first version, plus a few days of testing it on real requests with staff. Build it in this order:

1. Models and the state machine, with tests for every transition and every rule.
2. Request form, approval screens and audit timeline.
3. CSV export and batch tracking.
4. Email notifications.
5. Deployment and backups.

Before building, it's worth an afternoon trying a self-hosted low-code tool like Budibase or Appsmith. If one of them can enforce the approval order and an append-only audit log cleanly, it could save the build. Usually the separation-of-duties checks and audit guarantees are easier to get right in your own code.
