For eight users with a fixed two-step flow, a server-rendered Django app is the least work and the easiest to maintain. You get auth, forms, an admin UI, migrations and CSRF protection built in, so you only write the approval logic.

## Stack
- **App:** Django, with plain templates (optionally HTMX). No SPA.
- **DB:** SQLite in WAL mode is enough for eight people. Choose Postgres only if you already run it.
- **Serving:** gunicorn behind Caddy or nginx with HTTPS (internal CA or Let's Encrypt), run as a systemd service.
- **Auth:** Django's built-in username and password, with admin-created accounts and enforced password rules. Add TOTP (`django-otp`) later if you want it.

## Data model
- `User`: Django's user, plus a role flag for **requester**, **approver** and **finance/admin**.
- `Request`: title, vendor, amount, currency, description, requester, status, created_at, and an optional attachment (quote or invoice).
- `Approval`: request, step (1 or 2), assigned approver, decision (pending, approved or rejected), comment, decided_at.
- `AuditEvent`: append-only, with request, actor, action, before/after JSON, timestamp and IP.

## Workflow
`draft → pending_step1 → pending_step2 → approved → paid` (or `rejected`, `cancelled` from any pending state).

Rules to enforce in code, not just in the UI:
- Step 2 is only actionable after step 1 is approved.
- **The requester can't approve their own request.**
- **The same person can't approve both steps.**
- Editing a request's amount or vendor after submission resets it to step 1.
- Approved requests are read-only. Only finance can mark one `paid`.
- Put every status transition in one service function that does the check, the write and the `AuditEvent` in a single DB transaction. Views never set status directly.

## Audit trail
- Write an `AuditEvent` on every create, edit, decision, export and login or failed login.
- Make it append-only: no edit or delete in the admin, and no UPDATE or DELETE grants if you use Postgres.
- Show the history on each request page.
- Back up the DB nightly to a second location, and test a restore once.

- Columns: request ID, vendor, amount, currency, description, requester, approver 1 and 2 with timestamps, and approval date.
- Log each export as an audit event.

- Neutralise cells starting with `=`, `+`, `-` or `@` to prevent spreadsheet formula injection.

About 1–2 weeks for one developer, including tests for the approval rules. Those rules are the part to test most carefully.

1. Who are the approvers? A fixed pair, per-request choice, or amount-based thresholds? This is the main design question.

3. Is the server reachable only on your LAN or VPN? That's strongly preferable here.

# Recommendation: a small server-rendered web app on SQLite

For eight users and one workflow, keep the stack boring and have as few moving parts as possible.

## Stack
- **Language and framework:** Use whichever one someone on your team can maintain. Django (Python) is my default pick here. Its built-in auth, admin, forms, migrations and CSRF protection cover most of what you need. Rails and Laravel are equally good if you already know them.
- **Database:** SQLite in WAL mode. Eight users won't strain it. Backup is a file copy, using `sqlite3 .backup` on a nightly cron job. Move to Postgres only if you outgrow it.
- **Frontend:** Server-rendered HTML with plain forms. Skip the SPA.
- **Deployment:** One process behind Caddy or nginx with HTTPS, run by systemd or a single Docker container. Use an internal CA or Let's Encrypt, and restrict access to your LAN or VPN.
- **Login:** Local accounts with hashed passwords (argon2 or bcrypt). Add optional TOTP if you want a second factor. SSO isn't needed.

## Data model
- `User`: name, email, role flags (`requester`, `approver`, `finance`, `admin`), active.
- `Request`: requester, vendor, description, amount, currency, cost center or category, needed-by date, attachment (quote or invoice), status, `approver1`, `approver2`.
- `Approval`: request, step (1 or 2), approver, decision, comment, timestamp.
- `AuditEvent`: append-only log of who did what, when, and the before and after values.

**Status flow:** `draft → pending_step1 → pending_step2 → approved → paid`. A request can also end as `rejected` or `cancelled`.

## Rules that matter
- **Two ordered approvals:** Step 2 can't be actioned until step 1 is approved. Enforce this on the server, not just by hiding buttons.
- **Separation of duties:** Approver 1 and approver 2 must be different people, and neither can be the requester.
- **Lock after submission:** Editing the amount, vendor or description of a submitted request sends it back to step 1. Otherwise someone can change a request after it's been approved.
- **Rejections require a comment.**
- **Assign approvers:** Either the requester picks them or you use a fixed rule, for example by amount or department. Start simple.
- **Mark as paid:** Only the finance role can do this, and it records who and when. This prevents double payment.

## Audit trail
- Write an `AuditEvent` in the same database transaction as every state change, so you can't have one without the other.
- Make it append-only. In practice, no update or delete code paths exist, and a DB trigger blocks `UPDATE` and `DELETE` on the table.
- Record the actor, the timestamp in UTC, the action, the request ID, and a JSON diff of the fields that changed.
- Show the audit trail on each request page, and add an admin view with filters.
- For stronger tamper evidence, store a hash chain (each row includes the hash of the previous one). It's cheap and worth adding.
- Never hard-delete requests. Use `cancelled` instead.

## CSV export
- Export only `approved` and not-yet-`paid` requests, with filters for date range and status.
- Columns: request ID, date approved, vendor, description, amount, currency, category, requester, approver 1 and 2 with timestamps, and an attachment reference.
- Add an "export batch" record that stores who exported, when, and which request IDs. After exporting, finance marks the requests as paid, either individually or by batch.
- Guard against CSV formula injection. Prefix any cell starting with `=`, `+`, `-` or `@` with a single quote, since free-text fields flow straight into Excel.
- Use UTF-8 with a BOM if your finance team opens the files in Excel.

## Operations
- Send email notifications through your internal SMTP server when a request needs action. This matters more than it sounds, because requests stall without it.
- Back up the database and the attachments folder nightly, off the server, and test a restore once.
- Keep secrets in environment variables, not in the repo. Apply OS and dependency updates on a schedule.
- Add a handful of tests for the approval rules (ordering, separation of duties, edit-resets-approval). These are what you can't afford to get wrong.

Before you build, consider whether a self-hosted form and workflow tool would do the job. I haven't compared current options, so I'd check that before committing. I'd expect a first usable version in about one to two weeks for one developer.

4. What language or framework does your team already know?

# Recommendation: a small Django app on one server

For eight users and a simple workflow, use one Django app with SQLite or Postgres behind a reverse proxy. Skip microservices, a JS front end and a queue.

## Why Django
- It includes login, password hashing, sessions, CSRF protection, forms, migrations and an admin UI for managing users, so you write very little plumbing.
- It's boring and well documented, so whoever maintains it later can pick it up.
- Server-rendered pages are enough for this. Skip the SPA.

## Data model
- **User**: Django's built-in user, plus a role (requester, approver, finance/admin). You could also give each person a fixed first or second approver slot.
- **Request**: requester, vendor, amount, currency, description, attachment (invoice PDF), status, created_at.
- **Approval step**: request, step number (1 or 2), assigned approver, decision (pending, approved, rejected), comment, decided_at.
- **AuditEvent**: timestamp, actor, action, request, and before/after JSON. It is append-only.
- **ExportBatch**: who exported, when, and which requests were included.

## Workflow rules
Enforce these in code and cover them with tests.
1. Status flow: `draft → pending_step1 → pending_step2 → approved → exported → paid`. A rejection at either step ends in `rejected`, with a comment required.
2. Step 2 can't open until step 1 is approved.
3. The requester can't approve their own request, and the same person can't approve both steps.
4. Once submitted, the amount, vendor and payee details are locked. A change means cancelling and resubmitting, which restarts approval.
5. Do each state change in a single DB transaction, with a row lock, so two clicks can't double-approve.

## Audit trail
- Write an `AuditEvent` in the same transaction as every state change. Cover logins, submissions, decisions, edits, exports and admin changes.
- Make it tamper-resistant. Add a database trigger that rejects UPDATE and DELETE on the audit table, and give the app's DB user no rights to bypass it.
- Don't allow hard deletes of requests. Use a cancelled status instead.
- Keep the audit log in your backups.

## CSV export
- Export only `approved` requests that haven't been exported yet. Each export creates an `ExportBatch` and marks those rows `exported`, so nothing gets paid twice.
- Include the request ID, payee, amount, currency, reference, requester, both approvers and approval timestamps.
- Add a re-download link for past batches, and log every export.
- Prefix any cell that starts with `=`, `+`, `-` or `@` with a `'`. This prevents CSV formula injection when finance opens the file in Excel.
- Use Decimal or integer cents for money, never floats.

## Hosting and security
- Run it with gunicorn under systemd or Docker Compose, behind Caddy or nginx. Caddy gets you automatic HTTPS, with an internal CA or a Let's Encrypt cert if the host has a DNS name.
- Keep it on the internal network or VPN only. Don't expose it to the internet.
- Without SSO, use Django's password validators and lockout throttling (e.g. `django-axes`). Optional TOTP 2FA via `django-otp` is cheap and worthwhile, because this app approves payments.
- Store the secret key and DB credentials outside the repo.
- Back up nightly (`sqlite3 .backup` or `pg_dump`) to a different machine, and do a test restore once.
- Add email notifications for "your turn to approve" through your SMTP server. It's optional but is the thing that makes people actually use the app.

## Database choice
SQLite is fine for eight users, and it makes backups and deployment trivial. Choose Postgres only if you already run it. Triggers for the audit table work in both.

## Effort
A working version is roughly 1–2 weeks for one developer: models and state machine (2–3 days), pages and forms (2–3 days), audit and export (1–2 days), deployment and backups (1 day), tests and polish (2 days).

## Alternatives
- **Off-the-shelf** (a Google Form with approval add-ons, or a Jira/Airtable workflow): faster, but you lose "runs on our server" and a strict audit trail.
- **Node or Rails**: equally valid if your team already knows them. Familiarity matters more than the framework.

## Questions that could change the design
- Are the two approvers fixed per requester, or chosen by amount or department?
- Is there an amount threshold where a request needs only one approver?
- Do you need invoice attachments?
- Who runs the export, and who records that payment was made?
